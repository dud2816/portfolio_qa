CASE 01 · DATA 모니터링 중 발견

모바일 앱 PV 이상 트래픽 근본 원인 규명 · 필터링 정책

다들 좋은 신호로 지나친 PV 급증을 오류로 의심해, 재현 조건을 로그로 규명하고 방어책까지 설계한 사례
PROBLEM

Home 특정 섹션의 PV가 전 기간 대비 이상하게 높게 집계되고 있었습니다. 먼저 눈치챈 사람들도 있었지만, 지표가 오르는 모양새였기에 파고든 사람은 없었습니다. 저는 "좋은 시그널이 아니라 오류"라는 가설을 세우고 Databricks 로그를 직접 분석했고, PV가 1초 미만 간격으로 반복되는 패턴을 찾아냈습니다. 특정 channel_code에 집중되어 있었고, 유저 1인당 PV가 20–30회까지 발생하고 있었습니다.

HYPOTHESES → VERIFIED
H1 · 확인됨잠금화면 상태에서도 PV 발생 — lockscreen=true인데 attached=true인 엣지 케이스의 재현 조건을 규명
H2애드웨어·비정상 자동 실행 가능성
H3앱 크래시 루프에 의한 반복 실행 가능성
DECISION — 데이터팀 · 안드로이드 개발자 협업
  • 기존 로그로는 화면 꺼짐 상태를 구분할 수 없어, 안드로이드 개발자와 함께 screenoff 필드를 신설
  • 데이터팀과 적재 기준을 합의 — screenoff 상태에서 1초에 3–4회 이상 찍히는 PV는 적재 단계에서 제외
  • lockscreen=true 상태의 PV 제외 — 기본 필터
  • 앱 크래시 반복 루프에 Safeguard 적용 — 확인 시 프로세스 종료

정상 푸시 진입 유저 일부가 제외될 가능성보다 노이즈 제거 효과가 크다고 판단해 정책 적용을 제안했습니다.

CASE 02 · 0에서 만든 검증 체계

1인 QA — 금융 핵심 로직 검증 체계 구축

돈이 오가는 플랫폼의 품질을 혼자 책임져야 할 때 — 결함이 모일 곳부터 검증을 쌓은 사례
PROBLEM

부동산 조각투자 플랫폼의 QA는 저 한 명이었습니다. 청약·매수·매도·세금 계산 — 돈이 직접 오가는 로직은 결함 하나가 곧 금전 사고입니다. 모든 화면을 같은 깊이로 검증할 수는 없었고, 변수가 모이는 금융 로직에 힘을 집중하는 체계가 필요했습니다.

APPROACH
  • 검증을 기획 단계로 앞당김 — API 플로우 설계 리뷰에 QA로 참여해 오류를 릴리즈 전이 아니라 개발 전에 차단
  • Figma 기반 TC/시나리오 작성으로 릴리즈 전 결함률 감소
  • 청약/매수/매도/세금 계산 등 금융 핵심 로직의 시나리오를 설계·리딩 — 변수 조합이 많은 로직일수록 깊게
  • 화면만 믿지 않고 데이터로 이중 확인 — Postman/PAW로 API 응답, DBeaver로 회원 상태·거래 데이터 직접 검증
기획 리뷰 → 데이터 검증

혼자라서 만든 것이 아니라, 혼자여서 더 정확히 골라야 했던 검증 체계 — 기획 단계 리뷰부터 DB 검증까지 0에서 쌓았습니다.

CASE 03 · 반복 업무에서 발견

데일리 모니터링 자동화 — 1인 QA의 레버리지

1인 QA가 모든 걸 지킬 수 없을 때 — 지킬 곳을 고르고, 나머지는 기계에 맡긴 사례
PROBLEM → DECISION

서비스 신뢰성을 위해 매일 아침 30분–1시간의 수기 모니터링이 필요했습니다. 1인 QA로서 모든 것을 자동화할 수도, 모든 것을 지킬 수도 없었고 — 이 제약이 오히려 힘의 배분 기준(ROI)을 세우게 했습니다. 회귀 TC 중 ROI 관점에서 모니터링 케이스를 선별해 Appium 자동화를 구축하고 거래 시간대에는 상시 실행되도록 운영했습니다.

30–60분/일

반복 공수 절감 + 거래 시간 중 이슈 조기 검출 안전망. 확보한 시간은 금융 핵심 로직 검증에 재투자 — 뺀 힘을 리스크가 모이는 곳에 다시 쏟았습니다.

전환기 (2024 – 2025)

Q. 2년의 공백이 있네요?

좋아하던 반려동물 분야에 제대로 도전한 시간이었습니다. 애견미용사 3급(2024.12)과 2급(2025.08)을 취득하고 미용실 인턴으로 실무까지 경험했습니다.

그 과정에서 확인한 것은 오히려 저의 방향이었습니다. 혼자 완결하는 일보다 여러 직군과 협업해 품질을 함께 만들어가는 일에서 더 큰 즐거움을 느꼈고, 병행한 AI 스타트업(메이아이)에서 공간 라벨링의 데이터 구조를 설계하며 데이터·검증 감각을 이어갔습니다.

낯선 도메인을 빠르게 학습해 목표한 자격을 실행으로 옮긴 경험은, 낯선 제품·도메인도 빠르게 검증 체계로 만드는 QA의 힘과 맞닿아 있습니다.
